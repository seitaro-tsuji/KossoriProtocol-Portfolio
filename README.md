## 制作形態
5人チームで、企画・設計・素材選定・実装までを2日間で行い、ゲームを完成させました。

### 担当箇所
- ゲーム進行管理（開始・終了処理、タイマー制御、リザルトへの遷移）
- 他メンバーが制作したプレイヤー・マップ・敵キャラクター・アイテムなどのシーンへの配置・統合

    - スタンアイテムによる敵全体への効果適用
- シーン遷移処理およびフェードイン・アウト演出
- BGM・SEの管理・再生処理

## ゲーム概要
2D見下ろし型のステルスゲームです。

プレイヤーは、マップ内にランダムに配置された敵の視界を避けながらゴールを目指します。敵に接触したり、一定の条件で視界に捉えられたりするとゲームオーバーになります。

マップ内には移動速度を上げるアイテムや、すべての敵を一時的に停止させるアイテムが配置されており、これらを活用してゴールを目指します。

クリアタイムが記録されるため、より短い時間でのクリアを目指して繰り返し挑戦できるゲームです。

## 工夫した点
### 開発方針
制作期間が2日間と限られていたため、素材選定の時間を削減できるよう、Unityの標準的な図形を中心に使用しました。

また、「ゲームとして最低限成立する作品」をまず完成させ、残った時間で要素を追加していくという実装順を意識しました。

- 最低限の完成ライン
    - タイトル→インゲーム→リザルトの一連のゲームループの完成
    - インゲーム内から直接リスタートできる機能
    - 敵キャラクターの配置・移動・視点変更
    - 敵に見つかったときのゲーム失敗の処理

- 追加で実装できた内容
    - スピードアップアイテム・スタンアイテムの実装
    - マップ・敵・アイテムのランダム生成
    - サウンドの実装やアイテム取得時のテキスト演出
    - 連続クリア時のリザルト表記
    - ダッシュ中に敵に気づかれやすくなる仕様の追加
    
さらに、タイム短縮を目指して短いスパンで繰り返しプレイするゲームになるため、ゲーム終了から再スタートまでの時間をなるべく短くし、プレイする人がリプレイ時にストレスを感じないようにしました。

### 技術的な工夫
- ランダム生成時の重複防止

    `EnemyManager`および`ItemGenerator`では敵・アイテムのランダム生成を行っていますが、生成地点を単純に乱数で選択するのではなく、Fisher-Yatesシャッフルを利用して同じ候補地点が複数回選ばれないようにしています。

- スタン処理の管理

    `EnemyManager`では生成した敵をリストで管理し、スタン効果をまとめて適用しています。
    
    さらに、DOTweenのSequenceを利用して「スタン開始→解除前の点滅→解除」の一連の処理を実装しました。スタン中に再度スタンアイテムを取得した際は、既存のSequenceを停止することで解除処理の競合を防ぎました。


## 反省点
### ゲームデザインの面の反省点
短い制作期間で「何度も繰り返し遊べるゲーム」を目指したため、マップの形や敵・アイテムの配置などを全てランダム生成にした結果、プレイするたびに難易度が大きく変化するようになりました。
クリアタイムの短縮を目的に何度もプレイする場合、必要以上に運要素を含んでしまう点は今回の最大の反省点だと感じています。

今後同じ方向性のゲームを長期間で制作する場合には、シード値を利用したランダム生成を実装することで、リプレイ性を残しつつ、同じステージでタイムを競うこともできるようにするのが適切だと考えています。

### 実装面の反省点
開発時間を短縮するため、今回のソースコードでは`IngameManager`、`SceneChanger`、`AudioManager`などの管理クラスをシングルトンとして実装しました。
短期間で各機能を統合するうえでは便利でしたが、クラス間の依存関係が強くなりやすい構造になっています。長期的な開発では、イベントによる通知や参照の受け渡しなどを利用し、依存関係を整理する必要があると考えています。

また、`EnemyManager`、`ItemGenerator`ではあらかじめ決められた配置候補地点からランダムで選択して敵・アイテムを配置していますが、配置数が候補地点数を超えている場合の処理を省略しているため、堅牢性の面で課題があります。
